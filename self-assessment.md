# Professional Self-Assessment

Working through this program, and particularly through this capstone, changed how I think about my own code more than I expected. A significant part of this project involved going back and reviewing work I had already completed and been graded on, and finding real problems in it: a syntax error I had never caught, a bug that quietly kept a feature from working, and logic that could loop indefinitely under the wrong conditions. None of that was apparent when I originally submitted the work. It only became clear once I reviewed it critically instead of assuming it was fine simply because it compiled or ran. That is the clearest shift in how I approach this field now compared to when I started the program: writing something that works is not the same as writing something that is correct, and I have become far more deliberate about checking the difference.

I did not complete a formal team project during this program, so I cannot point to group development experience in the traditional sense. What I can point to is how I handled feedback. Every course involved submitting work, receiving notes, and being expected to apply them, not simply acknowledge them. I treated that seriously, since it mirrors the same dynamic I expect on any real engineering team, where a reviewer or lead identifies something I missed and the professional response is to address it rather than defend the original work. Several assignments also required explaining a technical decision to a hypothetical non-technical stakeholder, which meant describing what the code did and why it mattered without relying on jargon. That skill proved directly relevant to this capstone as well, since both the code review video and these written narratives require explaining real defects and design decisions to an audience that will not necessarily read the underlying code.

On the technical side, my coursework in data structures and algorithms required comparing options, vectors, hashtables, and trees, based on runtime complexity rather than familiarity. My software engineering and database coursework reinforced the same discipline from a different angle, emphasizing code that avoids unnecessary repetition and SQL that is not only correct but reasonably efficient and safe to run against real data. A dedicated secure coding course introduced a perspective I had not fully considered before, covering hashing algorithms such as SHA and explaining why storing something like a password in plain text is a genuine risk rather than a minor style issue. That understanding has stayed with me well beyond that course, and I now recognize the same kind of oversight in other code, including my own earlier work.

Taken together, what this program has given me is less a fixed skill set and more a habit: returning to my own decisions and evaluating whether they hold up, rather than assuming they do. That is what I intend to bring into the job search, not simply a list of languages and tools, but demonstrated evidence that I will identify and correct my own mistakes.

## About the Artifacts in This Portfolio

I selected three artifacts to represent the three areas this capstone is built around: software design and engineering, algorithms and data structures, and databases. All three originate from actual coursework rather than work created after the fact to appear impressive.

The first is a client management program I originally reconstructed from disassembled code in a reverse engineering course. The enhancement replaces a series of separate global variables with a proper class and vector, and in the process corrects a genuine bug in which a feature never functioned because the program never read the value it needed from the user. The second is pseudocode for a course advisor program from a data structures course, in which I originally compared a vector, hashtable, and tree by runtime complexity before selecting a hashtable; the enhancement adds a recursive traversal with cycle detection to correct a loop that could otherwise run indefinitely. The third is SQL work from a database course, where the enhancement corrects an actual syntax error I had previously missed, standardizes inconsistent query logic, adds indexing supported by measurable EXPLAIN comparisons, and wraps a destructive delete statement in a transaction so it cannot be made permanent by accident.

Each artifact demonstrates a distinct competency on its own, but the pattern across all three is consistent: take work I have already produced, evaluate it honestly, identify what is genuinely wrong with it, and improve it in a way I can clearly explain. That pattern, more than any individual fix, is what I want this portfolio to communicate.
